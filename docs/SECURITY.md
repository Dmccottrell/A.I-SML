# Emvryx security: what is built, how it works, what is left

This file is the single place for how Emvryx keeps people and their data safe. It grows as each part is built (the "Going public" checklist in [DEPLOY.md](DEPLOY.md) is the plan; this is the result). Plain rule of thumb: **today it is built for you and people you invite; the public-facing parts are being added in order, and the capacity and cost part (6) is on hold.**

## 1. Signing in (built: `auth.py`, `mailer.py`)

- **Keys are not stored.** A key is made once, shown once, and only its SHA-256 is kept in `users.json` (file mode 600). A stolen file cannot sign anyone in. An older file that kept the keys is converted the first time the server starts, and the old keys keep working.
- **The cookie is a session, not the key.** After a key, a pairing link or an email code, the browser gets `emvryx_session`: a random 256-bit token (HttpOnly, SameSite=Strict, Secure when the proxy says https). The server keeps only its hash, a coarse "where" (the first two parts of the address), and a device label like "Chrome on Android". A session lasts 90 days from last use (`session_days`).
- **Devices:** Settings > "Where you are signed in" lists every device and signs any of them out, or all the others. Rotating a key signs that person out everywhere. Turning a person off (ban) does too.
- **Pairing links** replace `?key=` links: `python app_server.py --pair owner` (or Settings > Owner > "make a sign-in link") makes `/pair/<token>`: valid 15 minutes, works once, becomes a session. The server prints one when it starts. `/?key=` still works (it turns into a session and drops the key from the address) but pairing links are the way now.
- **Email codes** (off until a mail server is set): 6 digits, 10 minutes, 5 tries, one live code per address, stored hashed. Set `EMVRYX_SMTP_HOST`, `EMVRYX_SMTP_USER`, `EMVRYX_SMTP_PASS` (and optionally `EMVRYX_SMTP_PORT`, `EMVRYX_MAIL_FROM`) before starting; the password is never written to a file. The same answer is given whether or not an address has an account, so nobody can probe who does. Owner: set a person's email when you add them. **Open signups** (anyone with a working email gets a free account) are off; to allow them, put `{"open_signups": true}` in `.emvryx/security.json`.
- Not built: sign-in with Google. It needs a Google client id and secret, which only you can create; the session code above is what it would plug into.

## 2. Guessing, lockouts, bans, the audit log (built)

- **Rate limits:** 8 wrong tries (key, pairing link or code) from one address in 10 minutes locks that address out of every key-based sign-in for the rest of the window (HTTP 429 with Retry-After), even for the right key. Asking for email codes is limited to 5 per 10 minutes per address and 3 per address of email. The address is the real caller's: behind the Cloudflare tunnel it is read from `CF-Connecting-IP`, but only when the request came from this computer (a trusted proxy), never from an outside caller.
- **Bans:** the owner can turn a person off (Settings > Owner > People): their devices are signed out at once and key, link and code sign-in are refused. The owner cannot be turned off.
- **Audit log:** the last 5,000 security events (sign-ins, failures, pairing, sign-outs, bans, key rotations, email codes) with the person, a coarse address and a short note, never a key, code or token. Owner only: Settings > People and the security log, or `GET /api/admin/audit`.

## 3. Browser protections (built)

- **Content security policy:** the page may run only its own script, identified by a fresh one-time nonce on every load (no `unsafe-eval`, no inline handlers, no other sites' scripts), and may load only its own files plus Google's font files; it cannot be framed (`frame-ancestors 'none'`, `X-Frame-Options: DENY`), cannot be made to submit forms elsewhere, and allows no plug-ins. Every JSON answer carries a policy that allows nothing. The page builds everything from text (no `innerHTML` with model or user text), so a model's reply cannot inject script.
- **HTTPS:** `Strict-Transport-Security` (one year) is sent whenever the proxy says the request was https (Cloudflare does), and the session cookie gets `Secure` then. A caller that is not the proxy cannot claim https.
- **Cross-site requests (CSRF):** every POST and DELETE is checked. A request a browser says came from another website (`Sec-Fetch-Site: cross-site`, a foreign `Origin`, or `Origin: null`) is refused with 403 and logged. The page's own requests and programs like curl (which are not browsers) pass. If the Cloudflare tunnel rewrote the Host header, `Sec-Fetch-Site` still identifies the page's own requests; to also accept an address by name, add it to `allowed_origins`. Cookies are also SameSite=Strict.
- **No keys in addresses:** `/?key=...` links are **off by default** (`allow_key_links`: set `true` in `.emvryx/security.json` to bring them back): the address is dropped at once with a note on the sign-in screen, because a key in a link ends up in history, logs and chat. Use a one-time pairing link, or paste the key in the sign-in box.
- Also: `Referrer-Policy: no-referrer`, `Cross-Origin-Opener-Policy: same-origin`, `Cross-Origin-Resource-Policy: same-origin`, `X-Content-Type-Options: nosniff`, a `Permissions-Policy` that turns off camera, microphone, location and payment, and `X-Robots-Tag: noindex` so search engines do not list a private app.

## 4. VryxCode in containers, quotas and who may use it (built; the container part needs Docker on your server)

- **Why:** the folder sandbox in `harness.py` stops a small model's mistakes, not a person attacking the server. With `--code-sandbox docker`, every command VryxCode runs (python, pytest, git) runs inside a throwaway container built by `code_sandbox.docker_prefix`: **no network at all**, all Linux capabilities dropped, `no-new-privileges`, a read-only filesystem plus a small `/tmp`, hard memory, CPU and process limits (so a fork bomb or memory hog is stopped by Docker), the server's own non-root user id, and **only that one project folder** visible. `--code-runtime runsc` adds gVisor if installed. Build the image once: `docker build -t emvryx/code-sandbox:1 docker/code-sandbox`; check with `python code_sandbox.py`.
- **Fails closed:** if the sandbox is wanted and Docker is not working or the image is not built, VryxCode **refuses to run** (for the owner too). It never quietly falls back to running on the host.
- **Who may use VryxCode:** the owner always (unless the sandbox is on and broken). Everyone else needs (a) VryxCode in their plan (`"vryxcode": true` per plan in `limits.json`: free is off, pro and mega are on), and (b) the container sandbox turned on. If you want to let trusted people use it without Docker, set `"code_unsandboxed_for_others": true` in `.emvryx/security.json`: you are then accepting that they can run programs as the server's user. The Code screen explains why when someone is not allowed.
- **Quotas per person** (all in `security.json`): 20 projects (`code_max_projects`), 100 MB per project (`code_project_mb`), 500 MB in total (`code_total_mb`), 3,000 files per project (`code_max_files`), 50 coding sessions a day (`code_sessions_per_day`) and 30 minutes per session (`code_session_minutes`). A session that outgrows its project or runs too long is stopped with its files kept; imports and zip uploads are checked against the same limits.
- **GitHub actions on the host are guarded too:** because a project folder can be written to by a container or a model, the server only runs git on it if its `.git/config` holds plain settings (remote URL, user name and email, branch tracking). Anything that can run a program or redirect the token (filters, fsmonitor, proxies, URL rewrites, includes, aliases, credential helpers, ssh commands, push URLs, hooks paths) makes the server refuse, with a plain message.
- Honest limits: Docker's isolation is strong but not perfect (a kernel bug can break out; gVisor reduces that); the Docker daemon itself is a powerful thing to expose, so run the app as an ordinary user in the `docker` group on a machine with nothing else precious, ideally a separate one from the models. This build could not be run against a real Docker daemon here (the tests check the command that is built, the refusal when Docker is missing, the quotas and the guards); run `python code_sandbox.py` and one coding task on your server before trusting it.

## 5. Connected accounts: encrypted tokens and "Sign in with GitHub" (built)

- **Encrypted at rest:** saved tokens are encrypted (`secret_box.py`, Fernet from the `cryptography` package: `pip install cryptography`) with a server key in `.emvryx/secret.key` (file mode 600) or the `EMVRYX_SECRET_KEY` environment variable, so the data folder alone, such as a backup, is useless. An older plain token is re-saved encrypted the first time it is read. If the key is lost or changed the token reads as "connect again", not a crash. Back up `secret.key` separately from the data folder. Without the package installed, tokens are kept as plain text in a mode-600 file and the connect screen says so; set `"require_encryption": true` to refuse instead.
- **Sign in with GitHub (no pasted token):** GitHub's device flow. In GitHub: Settings > Developer settings > OAuth Apps > New, tick **Enable Device Flow**, and copy the **client id** (it is public; there is no secret to keep). Give it to the server as `EMVRYX_GITHUB_CLIENT_ID` or `"github_client_id"` in `.emvryx/security.json`. Then Connected apps > GitHub shows **Sign in with GitHub**: the person gets a short code, types it at github.com/login/device and says yes; the server collects the token itself (the device code never reaches the browser) and never asks GitHub faster than it said. The scope is `repo`. Pasting a token still works.
- Connect, disconnect and sign-in starts are written to the audit log.
- Not built: GitHub App installation tokens with per-repository permissions (the narrowest option); other services (the Connected apps list keeps them "coming soon").

## 7. Your data rights, policies, backups and contact (built)

- **Download my data / Delete my account** (Settings > Your data; `data_tools.py`): a zip of plain files with everything held about the person (profile, settings, saved chats, kept notes, devices, GitHub activity log, VryxCode projects; never a key or a token), and a real deletion that removes chats, notes, projects, the GitHub connection, devices and usage rows, signs every device out, and replaces their name in the security log with "(deleted)". The owner account cannot be deleted this way. Both are logged.
- **Privacy and Terms pages** at `/privacy` and `/terms` (public; `web/privacy.html`, `web/terms.html`), linked from the sign-in screen and Settings. They describe what the code really does (what is kept and for how long, private chats never saved, no ads or trackers, hashed keys, encrypted tokens, the 5,000-event log, 90-day devices, 14 daily backups, web search only when it is on). Put your details in `.emvryx/security.json`: `"operator_name": "Your name or company"` and `"contact_email": "you@example.com"`; they fill the pages and add a "Report a problem" link in Settings. **Have a lawyer read both before you open to the public**: they are written in plain words but are not legal advice, and the age rule, governing law and liability wording depend on where you are. One statement needs your explicit yes: "chats are not used to train any model".
- **Backups** (`backup_data.py`): `python backup_data.py --data .emvryx --out backups` makes a dated zip (SQLite files copied safely while the app runs; mode 600; `secret.key` left out unless `--with-key`; the 14 newest kept, `--keep N`), and `--restore ZIP --to EMPTYFOLDER` restores it (refusing a non-empty folder and unsafe paths). Run it daily from Task Scheduler or cron and store the zips away from the server. Deleted accounts leave the backups as they age out.
- **Names:** an informal check is in [TRADEMARK.md](TRADEMARK.md): "Emvryx" looks distinctive, the five model names are common words already used around AI (always use them with the Emvryx stem), and a proper attorney-led search is still needed.

## Settings you can change (`.emvryx/security.json`, all optional)

`session_days` (90), `pair_minutes` (15), `login_fail_limit` (8), `login_fail_window` (600 seconds), `email_start_limit` (5), `email_start_window` (600), `open_signups` (false), `allow_key_links` (false), `allowed_origins` (`[]`), `code_unsandboxed_for_others` (false), `require_encryption` (false), `github_client_id`, `contact_email`, `operator_name` and the quota names above, `trusted_proxies` (`["127.0.0.1", "::1"]`; set `[]` if the app is reached directly and not through a proxy).
